5Service 2 — Backend (Spring Boot gateway)

The backend is the only component the browser can reach. It owns identity, ownership of data, safe file handling and the orchestration of long-running work. It contains no OCR, retrieval or prompt logic: for those it calls the AI service.

5.3 Security design

  • Stateless JWT. The token (HS256, signed with a secret of at least 32 bytes — the application refuses to start otherwise) carries the user id as subject plus e-mail and role. Default lifetime is 12 hours. JwtAuthenticationFilter validates it on every request and places an AuthUser in the security context. SessionCreationPolicy.STATELESS; no server session exists.
  • CSRF disabled on purpose. Credentials travel in the Authorization header, not in a cookie, so a cross-site form cannot attach them.
  • Passwords. BCrypt with cost 12. Passwords longer than 72 bytes are rejected rather than silently truncated (BCrypt’s limit). E-mail uniqueness is enforced case-insensitively by a unique index on lower(email).
  • Brute-force guard. LoginThrottle allows 5 failures per (e-mail + client IP) within 15 minutes, then returns HTTP 429. It is in-memory and therefore per instance.
  • Ownership by construction. Repositories expose methods like findByIdAndUserId. Requesting someone else’s document returns 404, not 403, so the API does not even reveal that the id exists.
  • Security headers on API responses: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer. CORS allows only configured origins and exposes Content-Disposition (needed by the draft download).

5.4 Upload handling (defence in depth)

  1. Reject empty files and files above the limit (25 MB by default; checked twice, once from the declared size and once while copying).
  2. Identify the file by its first bytes (magic numbers): PDF %PDF-, PNG, JPEG, TIFF, BMP, WEBP. The client-supplied name and MIME type are never trusted.
  3. Generate a random name (<userId>/<uuid>.<ext>), resolve the path and verify it stays inside the storage root (path-traversal check).
  4. Stream into a temporary file while computing SHA-256, then atomically move into place, so a crash never leaves a half-written file.
  5. Insert the database row; if that fails, delete the stored file so no orphans remain.

The original filename is sanitised before it is stored for display. The AI service re-checks the file type from bytes as well.

5.5 The document lifecycle

How the asynchronous job works

  • DocumentService.upload() stores the file and row, then calls start(). DocumentStateService.beginProcessing() is a small transactional method that refuses to start a second job for the same (document, language) while one is running, and refuses to redo a completed one unless force is set. That makes double-clicks and retries safe (idempotent).
  • DocumentProcessor.process() runs on the documentExecutor thread pool (2 core / 4 max threads, queue of 100). If the queue is full, the request does not hang: the result is marked FAILED with “The server is busy right now”. The HTTP request returns immediately with status PROCESSING.
  • The job: extract text via the AI service only if it is not already stored, save the extraction (text, page count, method digital/ocr/mixed, detected language), call /v1/simplify, save the JSON result and the model name, then capture deadlines.
  • One retry for transient failures (connection error, 5xx) after 2 seconds; client errors (4xx) and “LLM not configured” (503) are final.
  • Deadline capture is wrapped in its own try/catch so a bookkeeping error can never lose a finished explanation. Deadlines are captured only by the first language processed, so translating does not duplicate them.
  • StartupRecovery runs at start-up and marks any job left in PROCESSING by a crash or restart as FAILED (jobs wait in memory and are lost on restart), so users see a retryable error instead of a spinner that never ends.

5.6 The gateway client to the AI service

  • Three RestClient instances with different read timeouts: extract (300 s), simplify/chat/drafts (240 s) and health (3 s).
  • Every call adds X-Internal-Token. The client is forced to HTTP/1.1; the JDK client would otherwise try an h2c upgrade that uvicorn rejects, which corrupted multipart uploads during development.
  • Failures become AiServiceException. FastAPI’s detail text is passed to the user only for safe categories: 422 (for example an unreadable scan, or a draft form field problem) and AI errors tagged code: llm_* (bad key, rate limit, overloaded model). Anything else becomes a generic message, so internal details never leak.

5.7 Data model

Why JSONB for the AI result? The explanation is a document-shaped object (summary, lists of deadlines, references, sources) that the front end consumes whole. Keeping it as JSONB means the AI schema can evolve without a migration, while the fields the backend needs to query (deadlines) are also extracted into a proper relational table with an index.

5.8 Chat persistence

ChatService.ask() verifies ownership, refuses if the document has not been read yet (HTTP 409 NOT_READY), enforces a limit of 100 questions per document, loads the last 10 messages as history, calls the AI service and then saves the user’s question and the assistant’s answer. The assistant’s message stores the structured extras (answerable flag, quotes, cited sources, follow-ups, model) in the details JSONB column. The method is intentionally not transactional: an LLM call can take many seconds and must not hold a database connection.

5.10 Error handling

GlobalExceptionHandler maps every failure to one JSON shape (timestamp, status, code, message, fieldErrors): validation errors list the offending fields, upload size/type errors have stable codes, unknown routes are 404, and any unexpected exception is logged and reported as a generic 500 without a stack trace.

What happens if the AI service is down when a user uploads a file?

Upload still succeeds (the file is stored and the row saved). The background job’s call fails; after one retry the result is marked FAILED with the message “The AI service is not responding right now. Please try again shortly.” The user can press “process again” later. Login, history and deadlines keep working because they never call the AI service.

How do you prevent one user reading another user’s document?

All reads go through repository methods that include the user id (findByIdAndUserId), and a miss is reported as 404. The id comes from the verified JWT, never from the request. There is an integration test that tries to fetch another user’s document and expects 404.
