11Security and privacy

The system handles personal legal documents. The security design assumes the browser is untrusted, the AI service is internal, and the LLM provider is a third party.

11.1 Threat → mitigation

ThreatMitigation in this system
Reading another user’s dataOwnership-scoped repository methods (findByIdAndUserId); user id taken from the verified JWT; misses return 404; integration tests try cross-user reads, deletes and chat.
Stolen or forged tokenHS256 with a secret of at least 32 bytes (start-up fails otherwise); 12-hour expiry; front-end logout at expiry. Residual risk: token in localStorage (XSS) — see 4.3.
Password attacksBCrypt cost 12; 5-failure throttle per e-mail+IP; same message for unknown user and wrong password, and a dummy hash is compared for unknown e-mails so timing does not reveal whether an account exists.
Malicious uploadsContent-based type check (magic bytes), size cap, random stored names, path-traversal check, atomic writes, non-root containers; PDFs are only parsed by PyMuPDF/Tesseract in the AI service, never executed or served inline from the upload directory.
Direct access to the AI serviceNot published to the host; every route requires X-Internal-Token, compared in constant time; only the backend knows it.
SQL injectionJPA / parameterised queries everywhere. The one dynamically built SQL (IDF keyword search) only interpolates placeholders; the terms and weights are bound parameters, and terms come from a tokenizer that yields only letters and digits.
XSS / clickjackingReact escapes output; no raw HTML injection; CSP restricts scripts to the same origin; X-Frame-Options: DENY; nosniff; Referrer-Policy: no-referrer.
CSRFNo cookies are used for authentication, so there is no ambient credential to abuse; CORS lists only allowed origins.
Prompt injection via a documentThe model’s output is parsed against a strict schema and never executed; it cannot call tools or write data; citations and quotes are verified. A hostile document could still try to bias the summary, which is why the UI shows sources and caveats and says this is not legal advice.
Output injection into PDFs/WordUser text is HTML-escaped for the PDF renderer; Word receives plain runs; control characters are stripped by validation.
Secret leakageSecrets live in .env (git-ignored; only .env.example is committed); API errors never echo keys; the AI service strips quotes/spaces from keys and error messages name the setting, not the value.
Denial of serviceUpload size cap and nginx body limit; bounded async queue (overflow becomes a clear “server busy”); per-document chat limit; bounded form sizes for drafts; timeouts on every outbound call. (There is no global rate limiter — see limitations.)

11.2 Privacy considerations

  • What leaves the system. The extracted text of a document (and the retrieved legal sources) is sent to the configured LLM provider. Hosted providers may log or, on free tiers, train on inputs. For sensitive material use a local model (ollama) or a paid tier with a no-training policy. This should be disclosed to users in a real deployment.
  • What does not. Passwords (hashed), other users’ data, and draft forms.
  • Data minimisation and erasure. Users can delete a document or the whole account with cascading deletion of rows and files. Draft forms are never stored.
  • Planned improvement. Detect and mask phone numbers, Aadhaar numbers and e-mail addresses before text is sent to the LLM, and show the user what was masked.

11.3 Container hardening

  • Backend and AI service run as a non-root user (uid 10001); the backend and front end use multi-stage builds so build tools stay out of the runtime image; health checks on all services.
  • Only port 3000 is published. Database, backend and AI service ports are internal to the Compose network.
What is the biggest security weakness today?

Honest answer: the JWT in localStorage and the missing global rate limiter. The first is mitigated by CSP but a refresh-token-in-HttpOnly-cookie design would be stronger; the second means an authenticated user could submit many expensive jobs (bounded only by the queue and the file-size cap). I would add per-user rate limits, a Redis-backed throttle, and an account-enumeration review of the registration response (it reports “e-mail taken”).
